# 10. `useModule`

[kit/react/useModule.js](../../kit/react/useModule.js) — ~60 строк кода. Зачем он нужен и как
им пользоваться — [глава 08](../learn/08-react.md); здесь — каждая строка.

## Что это

Мост между React-компонентом и модулем кита: запускает модуль на DOM-элементе компонента и
убирает его, когда компонент исчезает.

## Что делает

- Запускает модуль после рендера, на элементе из `ref`.
- Передаёт настройки (`ctx.options`) и общий контекст из `KitProvider`.
- Не перезапускает модуль, если настройки те же по значению.
- Переживает двойной запуск StrictMode без «призраков».
- Корректно убирает ленивый модуль, если компонент исчез во время загрузки.
- Отдаёт экземпляр модуля через колбэк.

## Код по частям

### Ключ настроек

```js
const ids = new WeakMap()
let lastId = 0

export function optionsKey(options = {}) {
  return Object.keys(options)
    .sort()
    .map((key) => {
      const value = options[key]
      if (value !== null && (typeof value === 'object' || typeof value === 'function')) {
        if (!ids.has(value)) ids.set(value, ++lastId)
        return `${key}#${ids.get(value)}`
      }
      return `${key}=${JSON.stringify(value)}`
    })
    .join('&')
}
```

| Вход                                                    | Ключ                                                      |
| ------------------------------------------------------- | --------------------------------------------------------- |
| `{ autoplay: 5000 }` (каждый рендер новый объект)       | `autoplay=5000` — каждый раз одинаковый                   |
| `{ loop: true, speed: 2 }` и `{ speed: 2, loop: true }` | `loop=true&speed=2` — `sort()` убрал разницу в порядке    |
| `{ schema: callbackSchema }`                            | `schema#1` — номер **этой** схемы                         |
| `{ schema: s.object({…}) }` в теле компонента           | `schema#7`, потом `schema#8`… — новый объект, новый номер |

- `WeakMap` для номеров объектов — объект схемы, который больше никто не использует, не будет
  жить в памяти только из-за этой таблицы.
- Почему не `JSON.stringify` всего объекта? Функции он теряет (`onSubmit` исчез бы из ключа), а
  большие схемы сериализовывал бы на каждый рендер. Сравнение по ссылке — дёшево и честно.

### Состояние хука

```js
export function useModule(init, options, onInstance) {
  const ref = useRef(null)
  const callback = useRef(onInstance)
  const latestOptions = useRef(options)
  const kit = useContext(KitContext)
  const key = optionsKey(options)
```

- `ref` — его вы повесите на элемент; React запишет в `ref.current` DOM-узел после рендера.
- `callback` и `latestOptions` — тоже `useRef`: «коробки», содержимое которых можно менять, **не
  вызывая перерисовку** и не перезапуская эффекты.
- `kit` — контекст из `KitProvider` (или `null` без него).

### Эффект №1: свежие колбэк и настройки

```js
useEffect(() => {
  callback.current = onInstance
  latestOptions.current = options
})
```

Без массива зависимостей — выполняется после **каждого** рендера. Колбэк `onInstance` обычно
пишут стрелкой прямо в JSX — он новый каждый рендер. Если бы он был в зависимостях запуска,
модуль перезапускался бы постоянно. Здесь мы просто кладём свежую версию в коробку.

Эффект объявлен **раньше** второго — React выполняет эффекты в порядке объявления, поэтому к
запуску модуля в коробках уже свежие значения.

### Эффект №2: запуск и уборка

```js
  useEffect(() => {
    const el = ref.current
    if (!el) return undefined
    let alive = true
    let destroy = null
```

- Нет элемента (вы забыли повесить `ref` или элемент рисуется по условию) — ничего не делаем.
- `alive` — «этот запуск ещё актуален». Станет `false` в уборке эффекта.

```js
const ctx = Object.assign(Object.create(kit ?? { reduced: prefersReducedMotion() }), {
  options: latestOptions.current ?? {},
})
```

**`Object.create(kit)`**, а не `{ ...kit }`. У контекста есть «живой» геттер `scroll` (Lenis
появляется позже, см. `provider.jsx`). Распаковка `{...kit}` **вызвала бы геттер сейчас** и
заморозила `scroll: null` навсегда. `Object.create` делает `kit` прототипом: обращение
`ctx.scroll` в момент клика пройдёт по цепочке и вызовет геттер тогда.

```js
const run = (queues.get(el) ?? Promise.resolve())
  .then(() => (alive ? init(el, ctx) : null))
  .then((result) => {
    if (!alive) return result?.destroy?.()
    destroy = result?.destroy ?? null
    callback.current?.(result ?? null)
    return undefined
  })
  .catch((error) => console.error('[kit] useModule: модуль упал при запуске', error))
queues.set(el, run)
```

Цепочка обещаний на **элемент** (`queues` — `WeakMap` элемент → последнее обещание):

1. **Дождаться предыдущего** запуска на этом элементе.
2. **Отменили, пока ждали** (`!alive`) — не запускать вовсе.
3. **Запустить** (`init` может быть ленивым — тогда это сетевой запрос).
4. **Отменили, пока запускался** — сразу уничтожить созданный экземпляр.
5. Иначе — запомнить `destroy` и отдать экземпляр колбэку.

`catch` — упавший модуль не должен ронять компонент: ошибка в консоль, страница живёт.

```js
    return () => {
      alive = false
      destroy?.()
      callback.current?.(null)
    }
  }, [init, key, kit])
```

Уборка: пометить запуск неактуальным, уничтожить экземпляр (если он уже есть), сказать
колбэку «экземпляра больше нет».

Зависимости — **модуль, ключ настроек, контекст**. Не `options`: объект новый каждый рендер, а
`key` — строка, одинаковая при тех же значениях.

## StrictMode по шагам

```
рендер → эффект A (alive_A = true), queue = P_A
         уборка A (alive_A = false; destroy ещё null — модуль не запущен)
         эффект B (alive_B = true), queue = P_A.then(…B…)
P_A:  alive_A === false → init не вызываем
P_B:  ждёт P_A → alive_B === true → init(el) → экземпляр B
```

Модуль запущен **ровно один раз**. Без очереди ленивый модуль A мог бы запуститься после B и в
своём `destroy` снять то, что поставил B (реальный баг с `select`, описан в шапке файла).

## Что будет, если…

| Сделать                                  | Что сломается                                                              |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| `options` в зависимостях вместо `key`    | модуль перезапускается на каждый рендер                                    |
| `{ ...kit }` вместо `Object.create(kit)` | `ctx.scroll` навсегда `null` у модулей, запущенных до Lenis                |
| убрать очередь `queues`                  | в StrictMode отменённый ленивый экземпляр «портит» живой                   |
| убрать проверку `!alive` после `init`    | ушли со страницы во время загрузки — модуль работает на удалённом элементе |
| убрать эффект №1                         | колбэк `onInstance` из первого рендера — с устаревшими замыканиями         |

## Проверьте себя

1. Компонент рендерится 100 раз с `useModule(slider, { autoplay: 5000 })`. Сколько раз запустится
   слайдер?
2. Почему `optionsKey` сортирует ключи?
3. Что получит колбэк `onInstance`, когда компонент размонтируют?

<details>
<summary>Ответы</summary>

1. Один: ключ `autoplay=5000` не меняется.
2. `{ a, b }` и `{ b, a }` — одинаковые настройки; без сортировки ключи различались бы, и модуль
   перезапустился бы.
3. `null` — чтобы ваш `api.current` не держал уничтоженный экземпляр.

</details>
